# 02 · 알림 — Web Push · Edge Function · 설정 화면

밋업의 알림은 **"멤버가 뭔가 하면 관계된 사람 기기에 푸시가 뜬다"** 한 문장이다.
구현은 4층이고, 층마다 파일이 딱 하나씩이다.

```
도메인 함수 (lib/data/*.ts)
    └─ notify({type, workspace_id, actor_id, title, body, url, tag, target_user_ids?})
         ↓ supabase.functions.invoke('notify')
       Edge Function  supabase/functions/notify/index.ts
         ① 운영자 글로벌 토글 확인 (notification_admin)
         ② 수신자 결정 (target_user_ids 또는 역할 기반) → actor 제외
         ③ 개인 prefs 필터 (notification_prefs)
         ④ sendPushToUsers()
              ↓ VAPID + aes128gcm
            브라우저 푸시 서비스
              ↓
            public/sw.js  →  기기 알림  →  클릭 시 payload.url 로 이동
```

📄 **핵심 참고 파일**

| 층 | 이 폴더의 복사본 | 밋업 원본 |
| --- | --- | --- |
| 얇은 호출 래퍼 | `reference/src/lib/data/notify.ts` | `src/lib/data/notify.ts` |
| 구독 · 개인/운영자 설정 | `reference/src/lib/push.ts` | `src/lib/push.ts` |
| Edge Function 진입점 | `reference/supabase/functions/notify/index.ts` | 동일 |
| VAPID / 암호화 송신 | `reference/supabase/functions/_shared/push.ts` | 동일 |
| Service Worker | `reference/public/sw.js` | `public/sw.js` |
| PWA 매니페스트 | `reference/public/manifest.webmanifest` | 동일 |
| 개인 알림 설정 UI | `reference/src/features/notifications/notification-section.tsx` | 동일 |

## 1. DB — 테이블 4개

📄 전체 SQL: `reference/supabase/migrations/019_push_notifications.sql`

| 테이블 | 역할 | 키 |
| --- | --- | --- |
| `push_subscriptions` | 기기별 구독 (endpoint / p256dh / auth) | `unique(user_id, endpoint)` |
| `notification_prefs` | **사용자별** 마스터 스위치 + 종류별 토글(JSONB) | `pk user_id` |
| `notification_admin` | **워크스페이스별** 글로벌 토글(JSONB) — 운영자가 관리 | `pk workspace_id` |
| `notification_log` | 중복 발송 방지용 (선택) | `unique(user_id, type, ref_key)` |

**중요한 설계 2가지**

1. **한 사용자 = 여러 구독.** 폰·노트북·태블릿마다 endpoint 가 다르다.
   `unique(user_id, endpoint)` 로 upsert 하고, 발송은 그 사용자의 **모든** 행에 쏜다.
2. **누락은 곧 `true`.** `preferences` JSONB 에 키가 없으면 "받겠다"로 간주.
   그래야 새 알림 종류를 추가할 때 기존 사용자가 자동으로 받는다.

가입 시 기본 prefs 행이 생기도록 `handle_new_user()` 트리거에 한 줄 추가:

```sql
insert into public.notification_prefs (user_id)
values (new.id) on conflict (user_id) do nothing;
```

## 2. 클라이언트 — `notify()` 는 4줄짜리 래퍼다

📄 `reference/src/lib/data/notify.ts`

```ts
export async function notify(params: {...}): Promise<void> {
  if (isDemoMode()) return;
  if (!supabase) return;
  try {
    await supabase.functions.invoke("notify", { body: params });
  } catch (e) {
    console.warn("[notify] invoke failed", e);   // ← 절대 throw 하지 않는다
  }
}
```

같은 파일에 헬퍼 2개가 더 있고, 둘 다 자원 구분 없이 범용이다.

- `getActorName(userId)` — 표시 이름 (`name` → 이메일 앞부분 → `'누군가'`)
- `getParentCommentAuthor(table, parentId)` — 답글 알림 대상 조회

### 파라미터 의미

| 필드 | 뜻 | 빼먹으면 |
| --- | --- | --- |
| `type` | 알림 종류. 토글 키이자 필터 키 | 운영자/개인 토글이 안 먹음 |
| `actor_id` | **누가 일으켰나.** 이 사람은 수신자에서 제외 | **자기 행동 알림을 자기가 받는다** ← 가장 흔한 버그 |
| `target_user_ids` | 특정인에게만. 없으면 역할 기반 전체 | 담당자 전용 알림이 전원에게 감 |
| `url` | 클릭 시 이동할 **실제 라우트** | 알림을 눌러도 아무 데도 안 감 |
| `tag` | 같은 알림 덮어쓰기 키 | 같은 글에 알림이 5개 쌓임 |

> 테스트 알림처럼 **본인이 받아야 하는** 경우엔 일부러 `actor_id` 를 안 넘긴다.
> 📄 `notification-section.tsx` 의 `handleTestNotification` 참고.

## 3. 서버 — Edge Function `notify`

📄 `reference/supabase/functions/notify/index.ts`

필터가 **이 순서로** 적용된다. 순서가 바뀌면 결과가 달라진다.

```
① 운영자 글로벌 토글 (notification_admin.enabled[type])
       ↓ false 면 여기서 끝 (skipped: admin_off)
② 수신자 후보 결정
     target_user_ids 있으면 그것,
     없으면 getRecipients(type, workspace_id)
       · join_request / dev_message → owner+admin 만
       · 그 외 → owner+admin+member 전원 (guest 제외)
       ↓
③ actor 제외  candidateIds.filter(u => u !== actor_id)
       ↓
④ 개인 prefs 필터
     p.enabled === false           → 제외
     p.preferences[type] === false → 제외
     행이 없거나 키가 없으면       → 포함 (기본 수신)
       ↓
⑤ sendPushToUsers(finalIds, payload)
```

`getRecipients` 의 `default:` 분기가 "전체 멤버" 다. 새 알림 종류를 추가할 때
운영자 전용이 아니면 **아무것도 안 해도 된다.**

### 배포 주의 (밋업에서 실제로 겪은 것)

`_shared/` 를 import 하는 함수는 **Supabase 대시보드에서 배포하면 실패한다.**
CLI 로만 배포된다.

```bash
supabase functions deploy notify --project-ref <PROJECT_REF>
```

## 4. Service Worker + PWA

📄 `reference/public/sw.js`, `reference/public/manifest.webmanifest`

앱 부팅에서 한 번 등록한다 (`src/main.tsx`):

```ts
import { registerServiceWorker } from "@/lib/push";
registerServiceWorker();
```

📄 `reference/src/lib/push.ts` 의 `registerServiceWorker()` —
`window.load` 이후 등록 + 중복 등록 가드(`swReady`).

### iOS 는 조건이 까다롭다 (이식 시 반드시 안내)

- iOS **16.4+** 이고
- **홈 화면에 추가한 PWA** 에서만 푸시가 온다. 사파리 탭에서는 안 온다.
- 그래서 `manifest.webmanifest` + `apple-mobile-web-app-capable` +
  `viewport-fit=cover` 가 **알림의 전제 조건**이다. 디자인 이슈가 아니다.

권한이 `denied` 로 굳으면 코드로는 복구 불가 — 사용자가 브라우저 설정에서 직접
허용해야 한다. UI 에 그 안내를 띄워야 한다
(📄 `notification-section.tsx` 하단의 `perm === "denied"` 블록).

## 5. 알림 종류 카탈로그

📄 `reference/src/lib/push.ts` 의 `NOTIFICATION_TYPES` — **이 배열 하나가
개인 설정 화면과 운영자 설정 화면을 동시에 그린다.** 종류를 추가하려면:

1. `NOTIFICATION_TYPES` 에 `{ key, label, desc }` 추가
2. `notify.ts` 의 `type` 유니온에 추가
3. Edge Function 의 `EventType` 유니온에 추가 (운영자 전용이면 `getRecipients` 에도)

밋업의 현행 17종 (그대로 가져가되 이식 대상 도메인에 맞게 이름만 바꾸면 된다):

| key | 한국어 라벨 | 수신자 |
| --- | --- | --- |
| `join_request` | 가입 신청 | 운영자만 |
| `join_approved` | 가입 수락 | 본인 |
| `member_joined` | 새 멤버 입장 | 전체 |
| `new_meeting` | 새 일정 | 전체 |
| `new_note` | 새 회의록 | 전체 |
| `new_task` | 새 할일 | **담당자만** |
| `task_completed` | 할일 완료 | 전체 (본인 제외) |
| `new_insight` | 새 인사이트 | 전체 |
| `new_writing` | 새 글쓰기 | 전체 |
| `new_reading` | 새 챌린지 | 전체 |
| `new_agenda` | 새 안건·투표 | 전체 |
| `new_notice` | 새 공지 | 전체 |
| `attendance_reported` | 지각·불참 | 운영자만 |
| `guest_application` | 게스트 신청 | 전체 |
| `comment` | 댓글 | 관계자 (01 문서 3장) |
| `like` | 좋아요 | 관계자 (기본 **off**) |
| `dev_message` | 개발자에게 한마디 | 운영자만 |

> `like` 만 `notification_admin` 기본값이 `false` 다. 좋아요는 자주 발생해서
> 켜두면 시끄럽다. 원하는 사람만 켜게 한다.

## 6. 설정 화면 UI

📄 개인: `reference/src/features/notifications/notification-section.tsx`
📄 운영자: `reference/src/features/notifications/admin-notification-section.tsx`

개인 설정 화면 구조 — **내 정보 페이지 안의 한 섹션**이다. 별도 페이지 아님.

```
알림                                    ← label
──────────────────────────────────────  border-y + divide-y
푸시 알림                       [알림 켜기]   ← 마스터 (권한+구독)
  활성화됨 — 종류별로 아래에서 세부 조정
──────────────────────────────────────
테스트 알림 보내기                 [보내기]   ← ★ 반드시 넣어라
  도착 안 하면 권한 / VAPID 키 / SW 등록 점검
──────────────────────────────────────
가입 신청                            [토글]
  운영자에게 도착하는 신청 알림
… NOTIFICATION_TYPES 만큼 반복
```

**"테스트 알림 보내기" 버튼을 반드시 이식하라.** 푸시는 실패 지점이 6곳
(권한 / SW 등록 / VAPID 키 / 구독 저장 / Edge Function / prefs 필터)이라,
이 버튼 없이는 디버깅이 불가능하다. 밋업에선 이 버튼 하나로 문제 절반을 잡았다.

토글 스위치도 MUJI 톤이라 둥글지 않다 — `w-10 h-6` 사각형에 `w-5 h-5` 노브가
`translate-x-4` 로 이동. 켜짐이 `bg-accent-teal`, 꺼짐이 `bg-line-strong`.

## 7. 셋업 순서

```bash
# 1) VAPID 키 생성
npx web-push generate-vapid-keys

# 2) 프론트 환경변수 (.env.local + 배포 시크릿)
VITE_VAPID_PUBLIC_KEY=B...

# 3) Edge Function 시크릿
supabase secrets set VAPID_PUBLIC_KEY=B... VAPID_PRIVATE_KEY=... VAPID_SUBJECT=mailto:you@example.com

# 4) 마이그레이션 적용 (019 상당)
#    ※ 밋업은 대시보드 SQL 에디터로 수동 적용한다 (db push 금지)

# 5) 함수 배포
supabase functions deploy notify --project-ref <REF>

# 6) 앱에서 SW 등록 + 프로필에서 "알림 켜기" → "테스트 알림 보내기"
```

### 안 올 때 점검 순서

1. `Notification.permission` 이 `granted` 인가
2. `navigator.serviceWorker.ready` 이후 `pushManager.getSubscription()` 이 있나
3. `push_subscriptions` 테이블에 행이 들어갔나
4. Edge Function 로그에 `{ ok: true, sent: N }` 이 찍히나 — `sent: 0` 이면 필터에서 걸린 것
5. `notification_admin.enabled[type]` 이 `false` 아닌가
6. `notification_prefs` 에서 본인 토글이 꺼져있지 않나
7. **`actor_id` 에 본인을 넣고 본인에게 보내려 한 건 아닌가** (③에서 걸린다)
