## 1. 데이터 모델

자원 `X` 하나에 좋아요+댓글을 붙일 때 만드는 것은 **테이블 2개**뿐이다.

```sql
-- ① 좋아요 — 복합 PK 라서 중복 좋아요가 DB 레벨에서 불가능
create table public.x_likes (
  x_id       uuid not null references public.x(id) on delete cascade,
  user_id    uuid not null references public.user_profiles(user_id) on delete cascade,
  created_at timestamptz not null default now(),
  primary key (x_id, user_id)
);
create index x_likes_user_idx on public.x_likes(user_id);

-- ② 댓글 — parent_id 가 null 이면 최상위, 값이 있으면 그 댓글의 답글
create table public.x_comments (
  id         uuid primary key default gen_random_uuid(),
  x_id       uuid not null references public.x(id) on delete cascade,
  user_id    uuid not null references public.user_profiles(user_id) on delete cascade,
  content    text not null,
  parent_id  uuid references public.x_comments(id) on delete cascade,
  created_at timestamptz not null default now()
);
create index x_comments_x_idx on public.x_comments(x_id, created_at);
```

**설계 결정 3가지 (그대로 따르길 권함)**

1. **좋아요에 `id` 컬럼을 두지 않는다.** `primary key (x_id, user_id)` 가 곧
   "한 사람이 한 번만" 제약이다. 애플리케이션에서 중복 체크할 필요가 없다.
2. **답글은 1단계까지만.** `parent_id` 는 있지만 UI 는 답글의 답글을 만들지 않는다.
   트리 렌더링·들여쓰기 지옥이 사라지고, 6~20명 규모에선 이걸로 충분하다.
3. **`user_profiles(user_id)` 를 참조한다** (`auth.users` 아님). 그래야
   PostgREST 임베드(`author:user_profiles!x_comments_user_id_fkey(...)`)로
   작성자 프로필을 한 방에 조인할 수 있다.

### RLS — 4개 정책이 한 세트

```sql
alter table public.x_likes    enable row level security;
alter table public.x_comments enable row level security;

-- 읽기: 부모 자원이 내 워크스페이스면 OK
create policy x_likes_select on public.x_likes
  for select to authenticated using (
    exists (select 1 from public.x t
            where t.id = x_id and public.is_workspace_member(t.workspace_id))
  );

-- 좋아요 쓰기: 내 행만
create policy x_likes_insert on public.x_likes
  for insert to authenticated with check (
    user_id = auth.uid()
    and exists (select 1 from public.x t
                where t.id = x_id and public.is_workspace_member(t.workspace_id))
  );
create policy x_likes_delete on public.x_likes
  for delete to authenticated using (user_id = auth.uid());

-- 댓글 삭제: 본인 OR 워크스페이스 관리자 (모더레이션)
create policy x_comments_delete on public.x_comments
  for delete to authenticated using (
    user_id = auth.uid()
    or exists (select 1 from public.x t
               where t.id = x_id and public.is_workspace_admin(t.workspace_id))
  );
```

> `is_workspace_member` / `is_workspace_admin` 은 밋업이 001·002 마이그레이션에서
> 만든 `security definer` 헬퍼다. 이식 대상 앱에 동등한 멤버십 판별 함수가 없다면
> **먼저 그것부터 만들어라.** RLS 정책 안에서 테이블을 직접 select 하면
> 정책 재귀(infinite recursion) 에 걸린다.

### 답글을 나중에 추가할 때 (멱등 마이그레이션)

이미 댓글 테이블이 여러 개 있는 상태에서 답글 기능만 얹는 경우:

```sql
alter table if exists public.x_comments
  add column if not exists parent_id uuid
  references public.x_comments(id) on delete cascade;
```

`if exists` + `if not exists` 조합이라 **여러 번 실행해도 안전**하고, 아직 존재하지
않는 테이블은 조용히 건너뛴다. 전체 예시는
📄 `reference/supabase/migrations/048_comment_replies.sql`.

마지막에 `notify pgrst, 'reload schema';` 를 반드시 붙인다. 안 붙이면
PostgREST 가 새 컬럼을 모른 채 `parent_id` 를 무시한다.

## 2. 데이터 레이어 — 함수 5개가 한 세트

자원마다 아래 5개를 만든다. 이름만 다르고 몸통은 동일하다.

```
getXLikeState(xId, userId)  → { count, liked }
toggleXLike(xId, userId)    → boolean       + 알림
getXComments(xId)           → 작성자 조인된 배열
addXComment(xId, userId, content, parentId?) + 알림
deleteXComment(commentId)
```

📄 **가장 짧고 베끼기 좋은 원본** — `reference/src/lib/data/tasks.ts` 의
`ㅡ 좋아요 + 댓글 ㅡ` 섹션 (파일 하단).

### 좋아요 토글 — insert 시도 후 실패하면 delete

```ts
export async function toggleTaskLike(taskId: string, userId: string) {
  const { error } = await supabase
    .from("task_likes")
    .insert({ task_id: taskId, user_id: userId });
  if (error) {
    // 복합 PK 충돌 = 이미 눌러져 있음 → 토글 off
    await supabase.from("task_likes").delete()
      .eq("task_id", taskId).eq("user_id", userId);
    return false;
  }
  /* … 여기서 알림 발송 (아래 3장) … */
  return true;
}
```

"먼저 조회 → 있으면 delete / 없으면 insert" 로 하면 **왕복 2번 + 레이스 컨디션**이
생긴다. insert 를 먼저 던지고 PK 충돌을 토글 신호로 쓰는 게 정답.

### 댓글 목록 — 작성자를 한 쿼리로 조인

```ts
const { data } = await supabase
  .from("task_comments")
  .select(
    "*, author:user_profiles!task_comments_user_id_fkey(user_id, name, email, avatar_url)",
  )
  .eq("task_id", taskId)
  .order("created_at", { ascending: true });   // ← 오름차순 (오래된 것 위)
```

- **FK 이름을 명시**(`!task_comments_user_id_fkey`)해야 한다. 한 테이블에서
  `user_profiles` 로 가는 FK 가 둘 이상일 때 Supabase 가 어느 쪽인지 못 고른다.
- 답글도 같은 테이블이라 **한 번의 쿼리로 다 가져오고**, 트리 구성은 클라이언트에서
  한다(아래 4장).

## 3. 알림 배선 — "누구에게 보낼까" 규칙 3개

이 부분이 이식할 때 제일 자주 빠진다. 규칙은 셋뿐이다.

| 상황 | 수신자 | actor 제외 |
| --- | --- | --- |
| **좋아요** | 그 자원의 관계자 (작성자 / 담당자) | O |
| **최상위 댓글** | 그 자원의 관계자 | O |
| **답글** | **부모 댓글 작성자** (자원 작성자 아님!) | O |

"자원의 관계자"는 자원마다 다르다.

- 인사이트/글 → 작성자 1명
- 할일 → **작성자 + 담당자** 2명 (중복 제거)
- 안건·투표 → **전체 멤버** (토론이 목적이라 의도적 예외)

```ts
/** 할일 작성자 + 담당자 (actor 제외, 중복 제거) */
function taskNotifyTargets(task, actorId: string): string[] {
  return [task.created_by, task.assignee_id]
    .filter((id): id is string => !!id && id !== actorId);
}
```

### 답글 알림 — 부모 댓글 작성자 찾기

```ts
if (parentId) {
  const parentAuthor = await getParentCommentAuthor("task_comments", parentId);
  if (parentAuthor && parentAuthor !== userId) {
    await notify({
      type: "comment",
      workspace_id: t.workspace_id,
      actor_id: userId,
      title: "↳ 내 댓글에 답글",
      body: `${name} 님이 회원님의 댓글에 답글을 남겼어요: ${content.slice(0, 60)}`,
      url: `/tasks/${taskId}`,
      tag: `task-reply-${created.id}`,
      target_user_ids: [parentAuthor],
    });
  }
} else {
  /* 최상위 댓글 → 자원 관계자에게 */
}
```

`getParentCommentAuthor(table, parentId)` 는 테이블명을 문자열로 받는 **범용 헬퍼**라
자원마다 새로 만들 필요가 없다.
📄 `reference/src/lib/data/notify.ts`

### 알림 문구 규칙 (밋업 톤)

```
좋아요   title: "👏 좋아요"          body: "○○ 님이 「제목」 할일에 좋아요를 눌렀어요."
댓글     title: "💬 할일에 새 댓글"   body: "○○ 님: 본문 앞 80자"
답글     title: "↳ 내 댓글에 답글"    body: "○○ 님이 회원님의 댓글에 답글을 남겼어요: 앞 60자"
```

- 이름은 `getActorName(userId)` 로 뽑는다 (`name` → 이메일 앞부분 → `'누군가'`).
- `url` 은 **반드시 실제 라우트**. 이게 원칙 1(팝업 금지)이 필요한 이유다.
- `tag` 는 같은 알림이 중첩되지 않게 하는 키. 작명 규칙:
  `{자원}-{동작}-{자원id}[-{구분자}]` → `task-like-abc-uid`, `task-reply-cid`

## 4. UI — `LikeCommentBlock` 하나로 끝

📄 **파일 그대로 복사** — `reference/src/features/social/like-comment-block.tsx` (395줄)

### 이 컴포넌트가 이미 해결해 둔 것들

1. **낙관적 좋아요(optimistic update)** — 클릭 즉시 하트/숫자가 바뀌고 서버는 뒤따른다.
   `likePending` ref 로 더블클릭 시 토글이 두 번 도는 문제까지 막았다.
   실패하면 롤백. 부모가 리페치로 새 값을 줘도 **in-flight 중엔 덮어쓰지 않는다.**
2. **자동 높이 textarea** — `rows={2}` 로 빈 줄 여백이 생기는 문제 대신
   `scrollHeight` 로 한 줄에서 시작해 내용만큼 늘어난다. border-box 보정 포함.
3. **답글 트리 구성** — 평평한 배열을 받아 클라이언트에서 묶는다.
   ```ts
   const topLevel = comments.filter((c) => !c.parent_id);
   const repliesByParent = new Map<string, CommentRow[]>();
   for (const c of comments) {
     if (!c.parent_id) continue;
     const arr = repliesByParent.get(c.parent_id) ?? [];
     arr.push(c); repliesByParent.set(c.parent_id, arr);
   }
   ```
4. **삭제 권한** — `comment.user_id === currentUserId || canModerate`.
   관리자는 남의 댓글도 지울 수 있다.

### 시각 구조 (이대로 옮기면 밋업과 똑같이 보인다)

```
┌───────────────────────────────────────────────── border-t
│ [♥ 3]                                      댓글 5      ← 헤더 행
│
│  (avatar) 김대표  8월 21일 14:20
│           본문…                          [삭제] [답글]  ← 우하단 연한 박스
│  ─────────────────────────────────────── border-line/40
│      ↳ (avatar) 박이사  본문…                  [삭제]   ← ml-8, 연한 초록 콜아웃
│
│  [ 자동 높이 textarea                     ]  [ 등록 ]
└───────────────────────────────────────────────────────
```

- 좋아요 버튼: 안 눌림 = `border-line-strong text-foreground-muted` / 눌림 =
  `border-accent-teal text-accent-teal`, 문자는 `♡` ↔ `♥`.
- 답글 콜아웃: `ml-8 border border-accent-teal/70 bg-accent-teal/[0.05] px-3 py-2`
  + `↳` SVG 화살표. **답글임을 들여쓰기만으로 표현하지 않는 게 포인트** —
  모바일 좁은 폭에서 들여쓰기는 거의 안 보인다.
- 액션 버튼은 텍스트 링크가 아니라 **연한 네모박스**:
  `border border-accent-teal/40 bg-accent-teal/10 px-2.5 py-1 text-[11px]`.

### 페이지에 붙이는 법 (10줄)

```tsx
const [refreshKey, setRefreshKey] = useState(0);
const { data: likeState } = useAsync(
  () => (id && user ? getTaskLikeState(id, user.id) : Promise.resolve({count:0,liked:false})),
  [id, user?.id, refreshKey],
);
const { data: comments } = useAsync(
  () => (id ? getTaskComments(id) : Promise.resolve([])),
  [id, refreshKey],
);

<LikeCommentBlock
  liked={likeState?.liked ?? false}
  likeCount={likeState?.count ?? 0}
  onToggleLike={async () => { await toggleTaskLike(task.id, user.id); setRefreshKey(v=>v+1); }}
  comments={comments ?? []}
  currentUserId={user.id}
  canModerate={myRole === "owner" || myRole === "admin"}
  onAddComment={async (content, parentId) => { await addTaskComment(task.id, user.id, content, parentId); setRefreshKey(v=>v+1); }}
  onDeleteComment={async (cid) => { await deleteTaskComment(cid); setRefreshKey(v=>v+1); }}
/>
```

📄 실제 조립 예시 — `reference/src/pages/task-detail.tsx` (상단 훅 + 하단 렌더)

> **주의:** 편집 모드일 때는 `LikeCommentBlock` 을 렌더하지 않는다.
> `{mode === "view" && <LikeCommentBlock … />}`
