# 00 · 이식 원칙 — 먼저 못 박고 시작할 것

이 문서를 건너뛰고 01부터 시작하면, 코드는 다 들어갔는데 "밋업처럼 직관적이지
않다"는 결과가 나온다. 밋업의 직관성은 기능 목록이 아니라 **아래 6가지 구조 규칙**
에서 나온다.

---

## 원칙 1 — 팝업이 아니라 페이지다 ★ 가장 중요

밋업에는 "글쓰기 모달", "할일 추가 모달", "회의록 작성 모달"이 **없다.**
모든 쓰기·읽기 행위는 **자기 URL 을 가진 페이지**다.

```
/tasks              할일 목록
/tasks/:id          할일 상세      ← 여기서 편집 모드 토글 (같은 URL)
/notes              회의록 목록
/notes/new          회의록 작성    ← 페이지
/notes/:id          회의록 상세
/notes/:id/edit     회의록 편집    ← 페이지
/meetings/new       일정 등록      ← 페이지
/insights/new       인사이트 작성  ← 페이지
```

📄 **참고 파일** — `reference/src/pages/` 전체.
라우트 정의 원본은 밋업의 `src/router.tsx` (단일 소스, 플랫 배열).

### 왜 페이지인가

| 팝업일 때 | 페이지일 때 |
| --- | --- |
| 링크 공유 불가 | 알림 `url` 로 바로 그 화면에 착지 |
| 뒤로가기 = 앱 종료/이탈 | 뒤로가기 = 목록으로 (기대대로) |
| 모바일에서 키보드 올라오면 폼이 잘림 | 전체 화면을 다 씀 |
| 에디터·첨부·댓글을 다 넣으면 스크롤 지옥 | 섹션을 여유롭게 배치 |
| 새로고침하면 작성 내용 날아감 | URL 유지 + 임시저장으로 복구 |

**푸시 알림이 있는 앱은 팝업 UI 와 근본적으로 안 맞는다.** 알림의 본체는
"이 URL 로 가라"이기 때문이다. `notify({ url: '/tasks/abc' })` 가 성립하려면
`/tasks/abc` 가 실제 페이지여야 한다.

### 모달을 써도 되는 3가지 예외

밋업이 실제로 모달을 쓰는 곳은 이것뿐이다.

1. **첨부파일 뷰어** — 파일을 크게 띄우고 닫으면 원래 자리로.
   📄 `reference/src/features/attachments/attachment-viewer.tsx`
2. **로그인/회원가입 플로우** — 어느 페이지에서든 열려야 하므로.
3. **`confirm()` 수준의 확인** — 삭제 확인 등. 브라우저 기본 confirm 으로 충분.

이 셋 말고 "입력이 들어가는 모달"이 생기면 원칙 위반이다.

### 상세 페이지 안에서의 편집 = 모드 토글

새 URL 을 만들기 애매한 짧은 편집은 **같은 페이지에서 `mode` state 로 전환**한다.
팝업이 아니다.

```tsx
type Mode = "view" | "edit";
const [mode, setMode] = useState<Mode>("view");
...
{mode === "view" ? <ViewMode … /> : <EditMode … />}
```

📄 **참고 파일** — `reference/src/pages/task-detail.tsx`
(뷰/편집 토글 + 에디터 + 첨부 + 좋아요·댓글이 한 페이지에 다 들어간 표준형)

## 원칙 2 — 화면은 Supabase 를 직접 부르지 않는다

```
❌ 페이지에서  supabase.from('tasks').insert(...)
✅ 페이지에서  createTask(input, user.id)   ← lib/data/tasks.ts
```

`lib/data/*.ts` 의 **변경 함수 하나가 세 가지를 모두 책임진다.**

```ts
export async function createTask(input, createdBy) {
  const { data } = await supabase.from("tasks").insert(...).select().single();

  // ① 활동 피드 (필요한 경우)
  await recordActivity({ action: "created_task", ... }, createdBy);

  // ② 푸시 알림 (담당자에게만)
  if (data?.assignee_id) {
    const name = await getActorName(createdBy);
    await notify({ type: "new_task", ..., target_user_ids: [data.assignee_id] });
  }
  return data;
}
```

📄 **참고 파일** — `reference/src/lib/data/tasks.ts`, `insights.ts`,
`meeting-notes.ts`, `agendas.ts` (전부 같은 형태)

> **이식할 때 가장 흔한 실패:** 페이지 컴포넌트 안에서 insert 를 하고,
> 알림 호출을 "나중에 붙이자"고 미룬다. 그러면 알림 붙일 자리가 20군데로 흩어진다.
> 지금 한 곳으로 모아라.

## 원칙 3 — 알림은 "베스트 에포트", 절대 흐름을 막지 않는다

`notify()` 와 `recordActivity()` 는 **실패해도 throw 하지 않는다.**
푸시 서버가 죽어도 할일 저장은 성공해야 한다.

📄 **참고 파일** — `reference/src/lib/data/notify.ts` (try/catch + console.warn),
`reference/src/lib/data/activities.ts` (`/* logging is best-effort */`)

## 원칙 4 — 좋아요·댓글·답글은 자원마다 새로 만들지 않는다

테이블만 자원별로 두고(`task_likes`, `insight_comments` …),
**UI 컴포넌트는 딱 하나** (`LikeCommentBlock`) 를 재사용한다.
페이지는 콜백 4개만 넘긴다.

```tsx
<LikeCommentBlock
  liked={likeState?.liked ?? false}
  likeCount={likeState?.count ?? 0}
  onToggleLike={handleToggleLike}
  comments={comments ?? []}
  currentUserId={user.id}
  canModerate={myRole === "owner" || myRole === "admin"}
  onAddComment={handleAddComment}      // (content, parentId?) => Promise<void>
  onDeleteComment={handleDeleteComment}
/>
```

📄 **참고 파일** — `reference/src/features/social/like-comment-block.tsx`

## 원칙 5 — 데이터 페칭은 `useAsync` 하나로 통일

```tsx
const { data: task, loading } = useAsync(
  () => (id ? getTaskById(id) : Promise.resolve(null)),
  [id, refreshKey],
);
```

`refreshKey` 를 `useState` 로 두고 변경 후 `setRefreshKey(v => v+1)` 로 리페치.
`useAsync` 는 **재조회 중에도 이전 데이터를 유지**해서, 좋아요 누를 때 화면이
깜빡이며 스크롤이 맨 위로 튀는 문제를 막는다.

📄 **참고 파일** — `reference/src/lib/use-async.ts` (36줄. 그대로 복사)

## 원칙 6 — 색은 절제한다. 액센트는 한 가지 상황에만

밋업 UI 가 정돈돼 보이는 이유는 컴포넌트가 아니라 **색을 안 써서**다.
무채색 + hairline border 가 기본이고, 액센트 색(`--accent-teal`)은 셋만:

1. 브랜드 표식
2. **현재 위치** (활성 메뉴 · 활성 행)
3. **긍정 액션과 완료** (등록 버튼, 완료 체크박스, 진행률 바, 좋아요 눌린 상태)

📄 **참고 파일** — `reference/src/index.css` (토큰 정의 전체)
자세한 규칙은 `docs/guides/ai-office/design-system-guide.md` 참조.

> 이식 대상 앱이 자체 디자인 시스템을 갖고 있다면 색은 그 앱 걸 쓰되,
> **"액센트는 완료/활성/긍정 3곳만"** 규칙만은 가져가라. 이게 정돈감의 원인이다.

## 이식 순서 (이 순서를 지켜라)

각 단계가 끝날 때마다 **실제로 동작하는 상태**가 된다. 중간에 멈춰도 손해가 없다.

| 단계 | 내용 | 문서 | 완료 판정 |
| --- | --- | --- | --- |
| 1 | 공통 훅·토큰 (`useAsync`, `useDraft`, 색 토큰, `Avatar`) | 00 | 빌드 통과 |
| 2 | `activities` 테이블 + `recordActivity` + 활동 피드 페이지 | 03 | 아무 데이터나 만들면 `/activity` 에 뜬다 |
| 3 | 좋아요·댓글·답글 (자원 1개에만 먼저) | 01 | 인사이트 하나에 댓글/답글이 달린다 |
| 4 | 푸시 인프라 (SW · VAPID · Edge Function · 설정 화면) | 02 | 테스트 알림 버튼이 도착한다 |
| 5 | 데이터 레이어에 `notify()` 배선 | 01·02 | 남이 댓글 달면 알림이 온다 |
| 6 | 에디터 + 첨부 | 04 | 본문에 서식/이미지, 파일 첨부가 된다 |
| 7 | 할일 (목록·상세·배정·완료) | 05 | 배정하면 담당자에게 알림 |
| 8 | 일정 · 회의록 + 회의록에서 할일 배정 | 06 | 회의록 저장 한 번에 할일이 같이 생성 |
| 9 | 나머지 자원(기록/인사이트)에 3·6 반복 | 07 | 전부 같은 모양 |
| 10 | 개인 화면 (내 할일 / 내 활동 / 확인이 필요한 일) | 03 | 홈에서 내 할 일이 보인다 |

> **4번(푸시)을 3번(댓글)보다 먼저 하지 마라.** 알림 인프라만 있고 보낼 이벤트가
> 없으면 검증할 수가 없다. 반대로 3번 먼저 하면 5번에서 배선만 추가하면 된다.
